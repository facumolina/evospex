# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

EvoSpex is a search-based tool for inferring postconditions of Java methods. Given a target
Java method and a JUnit test suite exercising it, EvoSpex uses a genetic algorithm (JGAP) to
infer a postcondition assertion (in a JML-like expression language) that captures the method's
observed behavior, distinguishing valid ("positive") states from mutated ("negative") ones.

## Build & test

```bash
# Build the jar (target/evospex-1.0.1.jar) used by evospex.sh
mvn clean compile assembly:single
mvn test-compile

# Full package (used in CI, see .github/workflows/maven.yml)
mvn -B package --file pom.xml

# Run all tests
mvn test

# Run a single test class / method
mvn test -Dtest=StateGeneratorTest
mvn test -Dtest=StateGeneratorTest#testCollectedObjects_AvlTreeAdd_add
```

Requires Java 8 and Maven (source/target compiler level is 1.8). Test fixtures for example
subjects (case studies) live in `src/examples/java` and their JUnit suites in
`src/test/java/casestudies/**` — these compile alongside the main test sources.

## Running the tool end-to-end

EvoSpex works in two phases, both driven through `evospex.sh` (which wraps the assembled jar
on the classpath together with the subject-under-test's classpath):

```bash
# 1. State generation — produces input/output states in states/<class>/<method>/
./evospex.sh --genStates <subject_cp> <test_suite_fqn> "<method_soot_signature>"

# 2. Postcondition inference — evolves an assertion from the generated states
./evospex.sh --infer <subject_cp> <target_class_fqn> <method_states_dir> [popSize=n gens=g mp=m cp=c to=sec]
```

The method signature for `--genStates` uses Soot's bytecode signature format, e.g.
`"<casestudies.commonscollections.TreeList: void add(int,java.lang.Object)>"`.

## Architecture

The pipeline has three stages, each owned by a distinct package:

### 1. State generation (`evospex.StateGenerator`, `evospex.state.*`)
Uses **Soot** to load the compiled test suite class, finds every call site invoking the target
method, and instruments those call sites (`state.instrumentation.Instrumenter`,
`BytecodeUtils`) to serialize the receiver/arguments/result before and after the call. The
instrumented class is loaded via reflection and its `@Test` methods are executed
(`generatePositiveStates`), collecting objects into `state.StateSerializer`'s static lists
(`inputsThis`, `inputsArgs`, `outputsThis`, `outputsArgs`, `outputsResult`). `state.mutation.*`
(`StateMutator`, `FieldMutator`) then derives "negative" states by mutating fields/swapping
values on the positive output states (`generateNegativeStates`). Everything is serialized with
XStream (`utils.XStreamDeserializer`) into the `states/` directory, one folder per
class/method.

### 2. Target/expression analysis (`evospex.target.*`, `evospex.expression.*`, `evospex.utils.TargetInformation`)
Before search starts, `TargetInformation` builds a `target.TypeGraph` of the target class
(fields, reachable types, relations) and, by traversing it, enumerates the pool of candidate
expressions the GA can use: joined expressions (`e.f`), closured/quantified expressions
(`e.*f`, `e.*(f+g)`), cardinality and int expressions, etc. Expressions are represented via
`expression.Expr` (built by `expression.ExprBuilder` from ANTLR parse trees) and
`expression.symbol.*`. The grammar for the assertion language is
`expression/ExprGrammar.g4`; the generated lexer/parser/listener
(`ExprGrammarLexer/Parser/Listener/BaseListener`) are checked into
`src/main/java/evospex/expression/` rather than generated by the Maven build — **if you edit
`ExprGrammar.g4`, regenerate these classes with the ANTLR 4.7.1 tool and commit the
regenerated sources alongside the grammar change.**

### 3. Genetic algorithm (`evospex.ga.*`, `evospex.EvoSpexGA`, `evospex.EvoSpexParameters`)
Built on **JGAP** (`CustomConfiguration`). A `ga.chromosome.SpecChromosome` is an array of
`ga.chromosome.gene.*` genes, each wrapping a candidate `Expr` (assertion conjunct/atom); the
whole chromosome represents a candidate postcondition. `ga.chromosome.SpecChromosomesBuilder`
builds the initial population from `TargetInformation`'s expression pools.
`ga.operator.ExprGeneMutationOperator`/`ExprGeneMutationHelper`/`ExprGeneMutations` and
`ga.operator.ChromosomeCrossoverOperator` implement custom mutation/crossover over expressions
(replacing JGAP's defaults, wired in `EvoSpexGA.addCustomGeneticOperators`).
`ga.fitnessfunction.PostConditionSpecEvaluator` scores a chromosome by evaluating its
expression(s) against the positive/negative states (using
`expression.evaluator.*`/`expression.validator.*`), rewarding distinguishing valid from
invalid behavior while penalizing size. `EvoSpexGA.learnPostCondition` runs the evolution loop
(or a randomized-search fallback, `EvoSpexParameters.randomSearch()`) until
`gens`/`to` (timeout) is reached, reporting progress via `evospex.report.Report`/`Stats`.

### Entry points
- `evospex.StateGenerator` — phase 1 CLI entry (invoked via `--genStates`).
- `evospex.EvoSpex` — phase 2 CLI entry (invoked via `--infer`); parses `popSize`/`gens`/`mp`/
  `cp`/`to`/`unary`/`sizePenalty`/`mcaReward`/`random` flags into `EvoSpexParameters` and calls
  `EvoSpexGA.learnPostCondition()`.

### Output format
Postconditions are reported as JML-like assertions, e.g.
`assert(this.size = \old(this.size) + 1 && index in this.root.*(left).height && ...)`,
using `\old(...)` for pre-state references, `.*(...)` for transitive closures, `#` for
cardinality, and `in`/`not in` for set membership — mirrored by the grammar in
`ExprGrammar.g4`.

## Notes
- `src/examples/java/casestudies/**` holds the evaluation subjects (data structures under
  test, e.g. `TreeList`, `AvlTreeList`); `src/test/java/casestudies/**` holds their
  Randoop-generated regression test suites, which double as the "test suite" input to
  `--genStates`.
- `ConfigurationProperties` / `CustomConfiguration` centralize JGAP config and output file
  locations used across the GA package.
